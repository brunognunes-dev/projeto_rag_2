INSTRUÇÃO CENTRAL
Aja como um especialista em desenvolvimento web, engenharia de dados, RAG (Retrieval-Augmented Generation), Python e integração com bancos vetoriais, seguindo boas práticas de desenvolvimento de software.

O objetivo é desenvolver um projeto didático e funcional, no qual o aluno consiga compreender claramente cada etapa do processo de RAG, desde a ingestão dos documentos até a geração da resposta pelo LLM.

1. CONTEXTO DO PROJETO
Será desenvolvido um projeto RAG.

As informações referentes ao ambiente, versões, tecnologias e stacks obrigatórias estão descritas no arquivo:

<dados>
ambiente_stacks.txt
</dados>
Antes de iniciar qualquer implementação:

Leia e compreenda o arquivo ambiente_stacks.txt.
Respeite as tecnologias e versões especificadas nele.
Não substitua uma tecnologia definida no arquivo sem necessidade.
Caso exista conflito entre este prompt e ambiente_stacks.txt, analise o conflito e priorize as restrições explicitamente definidas no arquivo de ambiente.
O projeto possui finalidade didática, portanto o código deve ser claro, organizado e suficientemente comentado para que o aluno consiga compreender o fluxo executado.
Evite abstrações desnecessárias que escondam as etapas importantes do processo RAG.
2. ARQUITETURA E RESPONSABILIDADES
Utilize uma arquitetura clara separando:

Frontend
Interface do usuário.
Visualização das etapas do processo RAG.
Entrada da pergunta.
Seleção da base/documentos para ingestão.
Exibição dos resultados da recuperação.
Exibição da resposta final.
Backend
Regras de negócio.
Ingestão dos documentos.
OCR.
Extração e estruturação dos dados.
Tokenização.
Geração de embeddings.
Comunicação com o Supabase.
Recuperação vetorial.
Construção do prompt aumentado.
Comunicação com o LLM através do OpenRouter.
Retorno estruturado das etapas do processo para o frontend.
O frontend não deve conter regras de negócio ou lógica de acesso direto ao Supabase/OpenRouter.

3. SEGURANÇA E CONFIGURAÇÕES
As conexões remotas, incluindo:

Supabase;
OpenRouter;
estão definidas no arquivo:

.env
Regras obrigatórias:

Nunca expor as credenciais no frontend.
Nunca inserir chaves diretamente no código-fonte.
Nunca versionar ou imprimir credenciais nos logs.
O backend deve ser o responsável pelas conexões com serviços externos.
Utilize variáveis de ambiente para todas as credenciais e configurações sensíveis.
Regra específica para testes de conectividade
Ao criar scripts ou rotinas de teste de conectividade:

Não leia ou exiba o valor das credenciais.
Não faça print() das chaves.
Não registre tokens, senhas ou URLs contendo credenciais.
Apenas utilize a chave/entrada necessária para realizar a chamada de conexão.
O resultado esperado do teste deve informar somente se a conexão foi bem-sucedida ou não, juntamente com uma mensagem de erro segura quando necessário.
4. ORDEM OBRIGATÓRIA DE EXECUÇÃO
Siga a seguinte ordem:

Etapa 1 — Análise do ambiente
Leia ambiente_stacks.txt.
Identifique:
stack frontend;

versão do Python;
bibliotecas disponíveis;
banco de dados;
configurações;
restrições;
comandos de execução.
Verifique a estrutura existente do projeto antes de criar novos arquivos.
Etapa 2 — Teste do Supabase
Antes de criar o backend funcional, faça um teste de conectividade com o Supabase.

O teste deverá:

utilizar as configurações do .env;
verificar se o Supabase está acessível;
verificar se as credenciais são válidas;
verificar se existe comunicação com o banco;
não expor nenhuma credencial.
Regra:
Somente prossiga para a implementação do backend após um teste de conectividade bem-sucedido.

Caso o teste falhe:

não continue silenciosamente;
informe o erro;
identifique a provável causa;
corrija o problema quando estiver dentro do escopo;
execute novamente o teste.
5. BACKEND

O backend deverá ser responsável por todo o fluxo de RAG.

Organize o código de forma modular, separando, quando apropriado:

O fluxo deverá ser apresentado nesta ordem:

INGESTÃO
   ↓
TOKENIZAÇÃO
   ↓
EMBEDDING
   ↓
ÍNDICE VETORIAL
A interface deverá mostrar visualmente o andamento de cada etapa.

Sempre que possível, o frontend deverá receber do backend informações estruturadas sobre o estado da operação, permitindo demonstrar ao aluno o que está acontecendo.

Crie 4 documentos fictícios em formato PDF para utilização no projeto.

Os documentos deverão representar:

4 notas fiscais fictícias
Os documentos devem possuir informações suficientes para permitir consultas posteriores, por exemplo:

Os PDFs deverão fazer parte do ambiente de desenvolvimento para permitir testar todo o pipeline de ingestão.

8. OCR E EXTRAÇÃO DE DADOS
Utilize bibliotecas Python adequadas e eficazes para realizar OCR nos documentos.

O processo deverá:

Ler o PDF.
Identificar o conteúdo textual.
Aplicar OCR quando necessário.
Extrair os campos relevantes.
Estruturar os dados.
Preparar os dados para o processo de RAG.
Sempre que possível, preserve a relação entre:

Documento original
        ↓
Texto extraído
        ↓
Dados estruturados
        ↓
Chunks
        ↓
Embeddings
        ↓
Vetores
O projeto deve deixar essa relação clara para fins didáticos.

9. ESTRUTURAÇÃO TABULAR LOCAL
Após o OCR e a extração dos campos, estruture localmente os dados em formato tabular.

A estrutura deverá permitir visualizar claramente os dados extraídos das notas fiscais.

Exemplo conceitual:

documento

A estrutura final deve ser adaptada aos campos efetivamente encontrados nos documentos.

10. BANCO VETORIAL
O Supabase será utilizado como banco remoto.

Utilize PostgreSQL + PGVECTOR para armazenamento e recuperação dos embeddings.

O processo deverá:

Criar a estrutura/tabela necessária no Supabase.
Habilitar/utilizar o pgvector.
Definir a coluna vetorial com a dimensionalidade compatível com o modelo de embedding escolhido.
Armazenar:
identificação do documento;
metadados;
conteúdo/chunk;
dados estruturados relevantes;
embedding.
Criar a estrutura necessária para recuperação por similaridade.
Inserir os vetores gerados durante a ingestão.
Utilizar essa estrutura no processo de retrieval.
Não assuma a dimensionalidade do embedding: ela deve ser compatível com o modelo efetivamente utilizado.

11. EMBEDDINGS
Utilize FastEmbed para geração dos embeddings.

O modelo deverá ser adequado para o idioma e para o objetivo do projeto.

Antes de criar a estrutura vetorial definitiva:

identifique o modelo utilizado;
confirme a dimensão do vetor produzido;
utilize essa dimensão na coluna vector do PGVECTOR;
mantenha essa configuração centralizada para evitar inconsistências.
O processo deve permitir que o aluno compreenda:

Texto
  ↓
FastEmbed
  ↓
Vetor
  ↓
PGVECTOR
12. PÁGINA DE CONSULTA
Crie uma página específica para consultas.

A experiência deverá ser semelhante a uma interface de chat moderna, inspirada conceitualmente em aplicações como ChatGPT, porém com identidade visual própria.

A página deverá possuir:

campo para digitar a pergunta;

histórico visual da conversa, quando aplicável;
indicação de processamento;
resposta final;
visualização do processo RAG;
visualização dos documentos recuperados.
13. FLUXO DA CONSULTA
A página de consulta deverá representar visualmente o seguinte fluxo:

PERGUNTA
   ↓
TOKENIZAÇÃO
   ↓
EMBEDDING
   ↓
RETRIEVAL
   ↓
PROMPT AUMENTADO
   ↓
LLM
Cada etapa deverá ser identificável na interface.

O objetivo não é apenas retornar a resposta final, mas demonstrar didaticamente como a resposta foi construída.

14. RETRIEVAL
O processo de retrieval deverá utilizar busca vetorial no PGVECTOR.

Para cada pergunta:

gerar o embedding da pergunta;
consultar a base vetorial;
utilizar similaridade vetorial;
retornar top_k = 5;
apresentar os 5 candidatos recuperados, quando existirem;
apresentar seus respectivos scores de similaridade;
mostrar informações suficientes para identificar a origem do conteúdo recuperado.
Na interface, apresente algo semelhante a:

Resultado 1
Score: 0.XX
Documento: NF_001.pdf
Conteúdo: ...

Resultado 2
Score: 0.XX
Documento: NF_003.pdf
Conteúdo: ...
Os valores devem ser reais, provenientes da busca executada.

Não invente resultados.

15. AUSÊNCIA DE CANDIDATOS
Caso o retrieval não encontre candidatos relevantes ou não existam dados disponíveis na base:

Não crie, invente ou complete informações.

A resposta deverá ser exatamente:

Sem dados disponíveis na base
Essa regra deve ser aplicada antes da chamada ao LLM quando não houver contexto suficiente para responder.

16. PROMPT AUMENTADO
Quando houver candidatos relevantes:

Recupere os documentos/chunks.
Organize os resultados.
Construa o contexto.
Monte o prompt aumentado.
Envie o contexto juntamente com a pergunta para o LLM através do OpenRouter.
Gere a resposta utilizando somente as informações recuperadas quando a pergunta depender dos documentos.
O sistema deve evitar respostas inventadas ou informações que não estejam sustentadas pelo contexto recuperado.

Sempre que possível, deixe visível no modo didático a relação:

Pergunta
   +
Contexto recuperado
   ↓
Prompt aumentado
   ↓
LLM
   ↓
Resposta
17. OPENROUTER
A integração com o LLM deverá utilizar o OpenRouter.

As configurações devem ser obtidas através do .env.

Não exponha a chave do OpenRouter no frontend.

A chamada deverá ocorrer exclusivamente no backend.

O modelo utilizado deverá ser configurável, preferencialmente através de variável de ambiente, evitando deixar o nome do modelo espalhado pelo código.

18. SELEÇÃO DA BASE PARA INGESTÃO
